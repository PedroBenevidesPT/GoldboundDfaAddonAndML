# FarmAnalysis — zone farm finder

Scrape Wowhead drop tables per zone, join with TSM prices (`avgSalePrice`),
rank the best farms / transmogs / jackpots, and rotate camps to dodge
hyperspawn loot throttles.

---

## Start here: what this system is now

The sections below describe the farm finder, which is one part of it. This
section describes the whole thing and how to run it.

### The shared base: Postgres, Redis, pgAdmin

```powershell
docker compose up -d                 # postgres, redis, pgadmin
docker compose ps                    # all three healthy
docker compose up -d --scale worker=3   # three workers, no duplicate work
```

| service | role | why |
|---|---|---|
| `postgres` | **the authority** | leases, run history, shared stats and the market data itself live here; two workers can only agree on "who is doing what" through one database |
| `redis` | hot mirror | holds the counters a UI watches. It is never consulted to grant or veto a lease, so the pipeline runs with Redis absent |
| `pgadmin` | the UI | <http://localhost:5050>, the server is pre-registered, no login in desktop mode |
| `worker` | the pipeline | the same `run_pipeline.py`, built from `requirements.txt`. Scale it freely: the lease table decides which replica does each job |

Ports are offset in `.env` (`POSTGRES_PORT`, `REDIS_PORT`, `PGADMIN_PORT`) so
they do not collide with a local install.

**What lives where, today.** This is a migration in progress, stated plainly
rather than implied:

| data | backend now | note |
|---|---|---|
| `ah_auction`, `ah_snapshot`, `ah_realm`, leases, runs, stats | **Postgres** | copied and verified row-for-row; see below |
| `aggregate_meta`, `aggregate_partition`, `daily_*` | **Postgres** | built in whichever backend is configured; on a workstation that is still `data/aggregates.sqlite` |
| `tsm_*`, `blizzard_items`, DB2 facts, Wowhead drops | **Postgres** | on the stack; `tsm_markets.db` only exists as the TSM import file of a workstation run |

Every `--db` / `--blizz-db` flag below names the SQLite file for a
workstation run. With `DATABASE_URL` set they are ignored: the same tables are
read from the one Postgres database, which is the single source of truth on the
Docker stack.

### Moving the data, and proving it moved

```powershell
$env:DATABASE_URL="postgresql://goldbound:goldbound@localhost:5432/goldbound"
$env:WOW_PIPELINE_BACKEND="postgres"

python scripts/migrate_to_postgres.py --dry-run    # what would be copied
python scripts/migrate_to_postgres.py              # copy + verify
python scripts/migrate_to_postgres.py --verify-only
```

The SQLite file is opened **read-only**; the script cannot damage what it
copies. Each table is streamed with `COPY`, then checked on row count **and**
a content fingerprint, because a load that shifts every value by one column
keeps the count perfect. Foreign keys are suspended during the load (the
source never enforced them) and reported afterwards instead of being hidden.

The measured result on this dataset: **14,381,170 auctions at ~140,000
rows/s**, 19 tables, all verified, no orphans.

### One code path, two backends

`woweconomy/dbcompat` is what makes that possible without rewriting the ~130
`sqlite3.connect` call sites. With no configuration it returns a real
`sqlite3.Connection` — byte-for-byte the old behaviour, which is why the test
suite and a workstation run are unaffected. With `DATABASE_URL` set it returns
a `PgConnection` with the same surface and translates the SQL on the way
through: `?` placeholders, `INSERT OR REPLACE`/`OR IGNORE`, `sqlite_master`,
`strftime('%s', …)`, `PRAGMA table_info` and the SQLite type names.

Two translations exist because they are not cosmetic:

* `INTEGER` → `BIGINT`. SQLite integers are 64-bit, Postgres ones are 32-bit.
  A 99,999,999,900-copper auction does not fit in the latter.
* `CAST(x AS REAL)` → `CAST(x AS DOUBLE PRECISION)`. Postgres `REAL` is a
  4-byte float, so the market panel's weighted average turned 893,312,600 into
  893,312,576 — a silent change to every price the model trains on.

Three more are about *how* the two engines differ, and each one was found by a
failure rather than by reading the docs:

* **Identifier case.** SQLite matches identifiers case-insensitively, so the
  schema was free to call a column `itemId`; Postgres folds unquoted
  identifiers to lower case, so `SELECT itemId` looked for a column that did not
  exist. Migration `004` lower-cases the 32 mixed-case columns, which makes the
  two backends agree on the one form the code already writes, and `Row` matches
  names case-insensitively so `row["itemId"]` keeps working on both.
* **Generated keys.** `INTEGER PRIMARY KEY AUTOINCREMENT` hands out the next id
  on an INSERT that omits the column; Postgres has no implicit equivalent.
  Migration `005` gives the two AUTOINCREMENT keys a `GENERATED BY DEFAULT AS
  IDENTITY`, and `dbcompat.insert_returning_id` replaces `cursor.lastrowid`
  with `INSERT ... RETURNING` rather than looking the row up afterwards, which
  would be racy on a table two writers can touch.
* **Streaming.** A plain psycopg2 cursor materialises the entire result set
  inside `execute()`: the 17.4M-row auction join peaked at 12.6 GB and was
  killed. Row-returning statements now run on a named (server-side) cursor and
  are fetched in pages — 85 MB peak instead of 3,495 MB, for 17.2 s instead of
  13.9 s.

Anything with no faithful equivalent raises `UnsupportedSQL` and names the
construct rather than guessing. The conformance tests in
`tests/test_dbcompat_postgres.py` run the same statements on both engines and
compare results; they are skipped, not faked, when no Postgres is reachable.

### One database, three stores on a workstation

On the Docker stack there is **one** Postgres database. On a workstation with no
`DATABASE_URL` the same tables live in three SQLite files, created by the same
code path — a cache of the same schema, not a second implementation.

| store (Postgres: all one database) | what it holds | how it is built |
|---|---|---|
| `data/intel.sqlite` | auction-house snapshots straight from the Blizzard API, the relist decision ledger, plus the lease/run/stat tables the pipeline uses to coordinate (all of these are the one Postgres database on the stack) | `scripts/intel.py ah-fetch --all-realms` |
| `tsm_markets.db` | TSM's region and realm price tables, the account's own sale history, DB2 item facts, Wowhead zone drops | `scripts/fetch_tsm_snapshots.py` + `scripts/journal.py` |
| `data/aggregates.sqlite` | daily roll-ups, the statistical record that outlives the raw rows | `scripts/aggregates.py build --last-days 2` |

None of them is committed to git: they are derived, they are gigabytes, and
the schema is code, so a fresh checkout creates an empty store and refills it.
`.gitignore` states this and why.

Alembic owns the Postgres schema and nothing else creates tables there — a
`CREATE TABLE IF NOT EXISTS` outside the migrations lets a fresh database drift
from the baseline that defines it. `alembic upgrade head` on an empty database
reproduces the live schema exactly (the only difference is Alembic's own
version table).

### One command runs the pipeline

```powershell
python run_pipeline.py --once       # one cycle
python run_pipeline.py --loop       # keep cycling
python run_pipeline.py --once --workers 3   # up to three tasks at once
python run_pipeline.py --status     # what ran, what holds a lease, what failed
python run_pipeline.py --task fetch --dry-run
```

| task | cadence | what it does |
|---|---|---|
| `fetch` | 1 h | all 92 EU connected realms **and** the region-wide commodity book |
| `tsm_csv` | 6 h | the 187 TSM CSVs (92 realm groups + 3 region files), ten seconds apart |
| `aggregates` | 6 h | rebuilds the daily roll-ups for the last 2 days (`--last-days`, not `--days`) |
| `strategy` | 6 h | rebuilds the mog posting plan, so there is always one to read |
| `sentinel` | 24 h | retrains, gated by chronological validation |
| `decisions` | 6 h | replays stored scans into the relist ledger and attaches confirmed events |
| `export` | 6 h | writes `DFA_Estimate/Data/DFA_Estimate_Data.lua` |
| `visibility` | 24 h | were our own sales visible in the Blizzard auction book |
| `deploy` | after export | copies the toc-listed addon files into the game |

The TSM sweep is ten seconds between requests because TSM starts answering 429
without it: 187 files is 31 minutes of pacing, but a cold sweep of a republished
set is slower than the pacing (the CDN is the bottleneck), so the timeout is
three hours. The sweep is conditional (`ETag` / `If-Modified-Since`), so a run
where TSM has not republished costs 187 round trips and no bodies.

`aggregates` takes `--last-days`, which names a *window*. `--days` names
specific days, so passing it rebuilt every day in the store on every run — the
exact cost the windowed rebuild exists to avoid. A test pins the flag.

Every task holds a **lease** while it runs, so two pipelines started at once
do not fetch the same books twice. A lease expires, so a killed task cannot
block the pipeline. What is due is read from the configured store, not from a
timer, so a restart does not reset the clock and a missed tick is simply
overdue next time. Redis, if `WOW_PIPELINE_REDIS` is set, is a **mirror**: it
can never grant or veto a lease, and the pipeline runs with no Redis at all.

### Several tasks at once, without stepping on each other

The 187-file TSM sweep paces itself for half an hour, and a training run can
take longer. Running the cycle strictly one task at a time meant the exporter,
the ledger and the visibility report all waited behind the sweep — the
pipeline looked stalled for exactly as long as it was doing the most work.

`--workers N` (the container runs `--workers 3`) starts every task whose
`after` dependencies have finished, up to `N` at once. Dependency order is
still honoured: `export` waits for `strategy`, `deploy` for `export`. Each
worker gets its **own** connection (a psycopg2 connection is not shared
between threads), and the lease table still guarantees one worker per task, so
concurrency changes waiting, never correctness.

### Watching it

```powershell
python run_pipeline.py --status                 # one snapshot
python run_pipeline.py --status --watch 30      # refresh every 30 s
python run_pipeline.py --status --json          # for a monitor or a script
```

The snapshot lists every task with its last success, its cadence and its last
failure (time, exit code and the final line of output), the leases held right
now with how long each has been running, the state of the Redis mirror
(connected, how many keys, and any key in Redis that the database does not
have), and the last runs with their duration. `--json` returns the same view
as one object so a dashboard does not have to parse the table.

The worker also publishes `start` / `ok` / `failed` / `skipped` events on the
Redis channel `goldbound:events`, after the run row is written, so a monitor
can follow the pipeline live without polling:

```powershell
docker compose exec redis redis-cli subscribe goldbound:events
```

`strategy` needs the Data for Azeroth demand export (the `demand_*.csv`
files), which is an input rather than code. Point `DFA_DIR` in `.env` at its
folder; the worker mounts that folder read-only at `/app/woweconomy/dfa`. With
no `DFA_DIR` the task reports a **skip** (exit 78) instead of failing every
cycle — an empty plan is honest, a plan of guesses is not.

### Which source answers which question

Auction-house **snapshots** come from the Blizzard API: `fetch` walks all 92
connected realms plus the commodity book every hour and stores them in
`ah_snapshot` / `ah_auction`. The risk models train on that panel first
(`panel=blizzard`), and fall back to TSM's `tsm_snapshot` panel only when the
Blizzard panel is too short in rows or in span — the fallback is printed with
the reason, never silent. TSM remains the source of the **price path**
(regional and realm prices, sale rate) and the fallback when a Blizzard
snapshot does not cover an item or realm. Both are read through `dbcompat`,
so on the stack they are the same Postgres database.

A new dataset posts one alert (Discord via `DFA_DISCORD_WEBHOOK`, plus a
desktop toast) **when the bytes change**, not on every export. The digest is
only recorded once a channel actually accepted the alert, so a webhook that was
down does not lose it.

### Connected realms are the unit of the market

The auction house is shared per **connected realm**: 267 EU realm names are
92 books. A snapshot is stored once per book, and every reader resolves a
realm name through `ah.realm_match`, which matches the name *or* the
connected-realm id. Matching on the name alone made four of the five realms
in a group see an empty market, silently.

### The posting plan

```powershell
python scripts/strategy.py build          # the whole region market
python scripts/strategy.py build --limit 5000
python scripts/strategy.py show --action post --limit 20
```

`mog_valuation` answers "what is this worth" and `mog_strategy` answers "post it
or not, and at what price". Both were complete libraries with no caller, so the
second answer existed only if somebody imported it. `scripts/strategy.py` is
the caller: it takes the region market, asks the classifier which items are
transmog, values those, and stores the resulting plan in `mog_strategy_plan`
with the snapshot it was built from.

The plan is stored rather than computed on demand because the addon asks for a
price while the player is standing at the auction house. It cannot value
thirteen thousand items, and it must not receive a number derived from a
different snapshot than the one it thinks it is looking at. A stale plan is
visible as stale because it carries `built_at` and `as_of_snapshot`.

The table holds **the current plan**, not a history: a row that is no longer
planned disappears, or the addon keeps showing a recommendation the pipeline
has stopped making. An empty build does not wipe it — "nothing built" is not
the instruction "post nothing".

Measured on the live store after the SQLite readers were pointed at the shared
backend: 13,132 mog items planned from 31,184 region prices in 253 s. The
action mix is 6,724 `post_patient`, 3,189 `do_not_post`, 2,091 `maintain`,
601 `post`, 524 `undercut`, 3 `vendor`.

`undercut` carries the price it means. With a price-independent probability the
expected net gold rises with the price, so the best band candidate is always the
estimate — which meant an `undercut` recommendation could only ever quote a
price at or *above* the wall it said to beat. The price that beats the live wall
(one copper under it) is scored too, and the action and the price now come from
the same decision.

### The decision ledger

The relist advice ranks open listings today; the next scan produces a new
ranking and the old one is gone. That is enough to decide what to look at now
and not enough to answer the only question that matters later: did the advice
work? `woweconomy/intel/decision_ledger.py` records every recommendation with
its inputs **before** the outcome is known, then attaches the confirmed journal
event from `auction_events` / `auction_intel_events`.

```powershell
python scripts/intel.py decisions                         # read the summary
python scripts/intel.py decisions --backfill --link       # replay + attach events
python scripts/intel.py decisions --realm Dragonmaw --days 30
```

The table is `relist_decision` in the shared store (Alembic revision `006`).
It is append-only in spirit: a later scan supersedes the previous
recommendation for the same auction, rows are never deleted, and an outcome is
written once. Only `hold` and `watch` have an unconfounded natural outcome; a
cancel after `cancel_and_relist` is the advice being followed, not a failure,
and the summary says so instead of pooling everything into one sale rate. When
two open listings share item, character and price the ledger refuses to guess
and leaves both open with an `ambiguous` evidence line.

The pipeline runs `backfill --link` every six hours. The first full replay
recorded 1,773 scans and linked 36 outcomes; the rest stay open until a
confirmed event can be attributed to them. The record is young, and the
summary reports sample sizes rather than a conclusion.

### Are our sales in the Blizzard auction house?

```powershell
python scripts/sale_visibility.py --by-realm
python scripts/sale_visibility.py --realm Dragonmaw --limit 200 --strict
```

For every recorded sale it looks for a listing of the same item, on the same
realm, in a snapshot within a one-day lookback before the sale, and separates
three outcomes: seen in a snapshot, seen at exactly our price (consistent with
ours), and not seen. It reports its own **coverage** first, because a run where
the snapshots and the sales do not overlap cannot answer the question and a
plain "0 seen" would read like a finding about the market.

That is the current live answer: 557 usable sales span 2026-10-16 00:11 ..
2026-10-21 07:12 and the first snapshot was taken 2026-10-21 08:23 — seventy-one
minutes short of any overlap. The check runs daily so it becomes answerable the
first time a sale lands inside a snapshot period.

Why it matters: if our own listings are in the snapshot, the competition wall we
measure includes us, and an item we are the only seller of looks contested. A
match is evidence, not proof — two sellers at the same copper price are
indistinguishable and the API does not say who posted — so only a same-price
match is counted as consistent with ours.

### Farm ranking

```powershell
python scripts/farm_ranking.py zone             # full per-NPC report
python scripts/farm_ranking.py mats --top 20
python scripts/farm_ranking.py mogs --top 10
python scripts/farm_ranking.py realms --all-realms --top 10
```

There is exactly one implementation (`woweconomy/analytics/farm_ranking.py`)
and exactly one entry point (`scripts/farm_ranking.py`), which ranks nothing
itself. `realms` is the per-realm view: it answers the same question for each
auction house separately instead of once for the region, and it lives in its own
module because it batches the estimate over thousands of items instead of
calling `PricingEngine.estimate` per item.

Every mode prices from the same source. `resolve_market` decides: `auto`
prefers the trained model — a model answers with a realizable sale price *and*
the chance of selling, while a TSM average is a listing reference that says
nothing about whether anyone buys — with the market table kept as the per-item
fallback and the counts reporting how much of the ranking rests on which path.

The leaderboards used to read `tsm_region_price` directly, so the same item had
an asking price in one screen and a realizable price in another. Live now:
`farm_ranking.py mats` reports `1653 priced items (model (1653 estimate, 0
shipped, 0 fallback, 0 unpriced))` where it previously never consulted the
model at all.

## 1. Scrape zones


### O que os colecionadores ainda não têm

`woweconomy.analytics.collector_demand` cruza o teu inventário (ou os drops de uma
zona) com as wishlists do Data for Azeroth: `missing_pct` é a fatia da amostra de
colecionadores que **não** tem o item, `owned_pct` é a concorrência (quantos perfis
do DfA o têm) e `value` é `missing_pct x (100 - owned_pct) / 100` — procurado **e** raro.


O modo `item` responde a uma pergunta só: "e este item?" — aceita nome ou ID,
mostra se o tens na bolsa, o preço/liquidez do TSM, todas as entradas nas três
wishlists (com o aviso de que `id_cat` de uma aparência é um appearanceID, não o
itemID) e que NPCs das zonas carregadas o largam, com o EV por kill e a fatia que
é procura de coleção. `--no-zones` salta a parte dos drops; `--zones a.json,b.json`
escolhe os JSON a varrer; `--csv items.csv` grava uma linha por item consultado
(as mesmas colunas do relatório, mais `found` e `ev_kill`). Se o nome não existir, sugere os parecidos em vez de falhar em
silêncio.

O relatório de zona abre com a secção **`BoE QUE A AMOSTRA AINDA NAO TEM`**: uma
linha por item BoE (`sem/amostra`, falta%, drop%, preço, EV/kill, sr, spd, NPC),
ordenada por quantas contas ainda não o têm. É a medida por item que o `--faltam`
do `boe_targets` dá para o universo inteiro, aqui limitada aos drops da zona.

Segue-se o **`DROPS POR MOB`**: cada mob traz a sua linha agregada (`EV/kill`,
`EV coleccao` — a fatia de quem ainda não tem o que ele larga —, **`montra`** —
a soma do preço TSM de cada drop vendável do mob, uma vez cada: o que terias na
AH se listasses tudo o que ele larga; é um portfólio, somado sobre *todos* os
drops (mesmo os que `--mob-drops` esconde), não EV por kill nem promessa de
venda —, `falta%` — média das faltas dos drops do mob pesada pelo drop% —,
`falta/kill%` — probabilidade de
uma kill largar pelo menos um item que a amostra ainda não tem —, `pago/tot`) e,
por baixo, **os drops do mob por ordem de quem os ainda não tem**: o primeiro de
cada mob é a **montra** (o drop que mais contas da amostra não têm), com
`sem/amostra`, `falta%`, `drop%`, preço e `EV/kill`. A lista de mobs segue a
mesma ordem (montra primeiro), portanto o topo do relatório é o mob cujo melhor
drop mais gente ainda precisa. O EV de um mob usa a taxa *dele*: um item largado
por dois mobs entra nos dois, com o drop% de cada um, e não com o melhor dos
dois. O mob que não tem preço não desaparece — fica com `EV 0g` e a contagem
visível. `--mob-drops N` decide quantos drops de cada mob aparecem (3 por
omissão, `0` = todos e `--top N` quantos mobs).

### Ids para grupos do TSM

O modo `ids` faz a mesma análise da zona e imprime só ids: **um grupo do TSM por
linha**, no formato `i:<id>,i:<id>,...` do TSM 4, pronto a colar no Import do
grupo. As bandas
são cortes de operação, não os `COLECTOR`/`NICHO` das tabelas, e o número de
separações é o número de cortes em `--cuts`: `85,65` (o default) faz três grupos
(`85+`, `65-85`, `<65`) e `85,75,65,55` faz cinco (`85+`, `75-85`, `65-75`,
`55-65`, `<55`). Um corte é um limite inferior **inclusivo** (um item com 85,0%
entra em `85+`), a ordem no `--cuts` não interessa e cortes repetidos são um só.
`--band` escolhe as linhas pelo rótulo (`65-75`), pela posição (`2`), pelo nome
antigo (`alta` = primeira, `nicho` = segunda, `comum` = a última) ou com
`todas`; o default é `alta,nicho`. Ficam de fora, como no EV, as linhas
era-Classic, os BoP e os itens sem linha nas wishlists; cada id aparece uma vez,
ordenado pela falta. `--out-prefix mogs` grava um ficheiro por banda
(`mogs_85plus.txt`, `mogs_75-85.txt`, …) com exactamente a linha a colar.

```powershell
REM 5 grupos
python -m woweconomy.analytics.collector_demand ids woweconomy/wowhead_zones/zone_331.json woweconomy/wowhead_zones/zone_16.json --db tsm_markets.db --cuts 85,75,65,55 --band todas --out-prefix mogs
```

```powershell

python scripts/tsm_groups_export.py --write   # reports/mog_groups/mogs_groups.tsm (referência regional)
```

É uma linha `AceSerializer` (`^1^T...`) que se cola em `Groups -> Import`; cria
`Liquid`, `Collector`, `Slow`, `Very_Slow`, `Unproven`, `Unknown`, `Conflict` e
as operações `Mogs ...` com as strings da secção D de `reports/mog_groups.md`.
As operações ancoram no **mercado regional** (`dbregionmarketavg` →
`dbregionhistorical` → `dbhistorical`), nunca no `dbmarket`/`dbminbuyout` do reino
— num reino sem concorrência o teu próprio anúncio *é* o mercado e o preço
ficaria congelado no primeiro valor — nem no `dbregionsaleavg` (média de vendas,
contaminada por snipes). O factor é **bandado** por `ifgt` (500 g / 5 000 g /
50 000 g) e sobe com a banda; `unknown` não posta (`postCap 0`). O `--realm`
aplica o perfil medido do reino (factor local medido, postura, duração e janela
de retenção no `maxExpires`): o `mogs_groups.tsm` sem `--realm` é a referência
regional, e cada reino com perfil tem o seu ficheiro.

O `mog_groups` classifica **por aparência**: as variantes que partilham o look
ficam no mesmo grupo mesmo que só uma tenha preço, e as variantes de sufixo
aleatório (“... of the Fireflash”) seguem o id base (`i:9768`), que é o que o TSM
usa. `--items all` (default) agrupa os 127 155 itens com aparência (os looks sem
preço ficam `unknown`); `--items variants` limita aos 38 746 com preço no look.

**Por id quando o id existe** (aparências): o `db2_item_appearance` liga o item
às suas aparências e o `dfa.db :: missing` diz quantas contas da amostra ainda as
não têm -- os dois lados falam appearanceID. O modo `zone`/`inventory` usa essa
ponte primeiro e só cai no nome quando o item não tem aparência nenhuma
(receitas, lixo, quest). No Ashenvale isto mudou **571 -> 881** itens com
procura (gap >= 50%: 502 -> 655) e a fatia de EV atribuível a colecionadores
**36% -> 41%**, com os mesmos 1.071 itens: os 310 que faltavam eram aparências
que o nome não encontrava.

O join **por nome** continua a ser o único possível para `mounts.id` (mountID) e
`recipes.id` (recipeID) — e os ids de aparência partilham o intervalo numérico
dos ids de item, portanto juntar drops por número *sem* a ponte "acerta" em ~80%
por coincidência. `~` à frente do nome significa que o sufixo aleatório
foi removido ("Pagan Britches of the Fireflash" -> "Pagan Britches": a mesma
transmog).

#### Motor de preço baseado em evidência

O modelo de preços do projecto fixa um coeficiente por banda de preço sobre
preços de anúncio. O `scripts/pricing_engine.py` faz o contrário: estima, item a
item, o **valor realizável** a partir de uma média aritmética ponderada pela
qualidade da evidência, e devolve três saídas separadas — o valor estimado
(com intervalo, confiança e proveniência), a **liquidez** e o **preço de
listagem recomendado**.

```powershell
python scripts/pricing_calibration.py --write   # mede o peso de cada fonte
python scripts/pricing_engine.py --write --backtest
```

O princípio é explícito: **os anúncios mostram o que os vendedores querem
receber; as transacções mostram o que alguém pagou**. Por isso as fontes de
anúncio e as de venda não são misturadas — o valor de transacção vem primeiro e
as referências de mercado são confrontadas com ele. Os pesos saem de
uma **calibração** contra as vendas reais da conta, não de constantes: a
calibração mede que o ask local é, em mediana, **3,9× o preço realizado**, e o
que isso implica.

Os relatórios ficam em `reports/pricing_engine/` (calibração, estimativas
item a item, walk-forward). Nada é importado no TSM.

### Token Rush: liquidar o inventário com prazo

Quando o objectivo deixa de ser o valor do item e passa a ser **ter ouro em
12 dias**, o modelo normal não serve: é preciso um perfil do item, uma postura
do reino e um factor de prazo, e o resultado tem de caber num orçamento de
horas. Isso é o `scripts/token_rush.py`, que funciona em modo *dry run* e não
toca em nada dentro do jogo:

```powershell
python scripts/token_rush.py                                # fila e défice
python scripts/token_rush.py --write --export --flipqueue   # relatório + ficheiros
python scripts/token_rush.py --feedback                     # o que foi realmente vendido
```

| ficheiro | o que é |
|---|---|
| `reports/token_rush/token_rush.md` | o relatório da campanha (estado, postura por reino, fila, marcos dos dias 3/6/9/12, bloqueios) |
| `reports/token_rush/rush_queue.csv` | a fila: uma linha por item×reino com perfil, evidência, preço, piso e avisos |
| `reports/token_rush/flipqueue_<reino>.csv` | lista para o FlipQueue (`Sell Price` = preço recomendado, `Sell Realm` = reino alvo) |
| `reports/mog_groups/liquidity_mogs_groups_<reino>.tsm` | import do TSM com **um grupo e uma operação por item** |
| `reports/token_rush/feedback.md` | preço recomendado vs preço a que vendeu, e a taxa de venda observada |

As regras: o **perfil do item** (A líquido, B procura provada, C especulativo,
D estoque parado, U desconhecido) sai de evidência — as vendas e expirações da
própria conta — e nunca do preço; a **postura do reino** é uma dimensão
separada (nível local, concorrência, avisos de dados: reinos com métricas
idênticas são o mesmo mercado); o **preço de rush** é a referência local com a
banda de undercut (pela concorrência), o factor do item (pela evidência) e o
factor de prazo (pelo calendário), entre um piso (valor de venda ao fornecedor
e limite de perda) e um tecto (a referência). A fila ordena por contribuição
para o défice por hora de gestão, e o valor esperado só aparece quando existe
histórico de venda do próprio item — quando não existe, a linha diz
*heurística* e a ordem usa um peso de evidência, não uma probabilidade.

### Quais BoE ainda faltam aos coleccionadores


`--faltam` é a leitura simples: **uma linha por item**, com `sem/amostra` -- quantas
das contas sondadas não trouxeram a aparência na resposta, ou seja, quantas ainda
não têm o item. Sem colunas de aparência. A posse é medida pela aparência que o
item concede porque é o que o DfA expõe: se a aparência não veio, o item de
certeza não veio (o inverso não se pode afirmar -- a conta pode tê-la por outro
item).

O join e' **por id dos dois lados**, e e' isso que o torna exato: o
`ItemAppearance.ID` do cliente e' o mesmo `visualid` do catalogo do Data for
Azeroth, portanto `db2_item_appearance` liga item -> aparicao sem passar por
nomes. O preco/liquidez vem do TSM.

| estado | o que significa | itens |
|---|---|---|
| `falta` | pelo menos uma das suas aparências ainda falta a amostra | **14.868** (91,3%) |
| `inobtenivel` | todas as aparências vêm de fonte morta no catálogo do DfA | 239 |
| `fora_catalogo` | têm aparência, mas nenhuma está no catálogo | 13 |
| `comum` | aparência obtível e já todos a têm | 0 |
| `sem_aparencia` | não tem linha de aparência: receita, anel, trinket, token | 1.166 |

`inobtenivel` merece a distinção: o BoE continua a vender-se (quem o compra
passa a ter a aparência), mas o DfA nunca lhe chama procura porque a fonte
listada está morta -- sem o catálogo estes 239 caíam no balde "comum", que era
o que acontecia antes de irmos ver a flag `unobtainable`.

### Onde (que reino) esses mog valem mais

A demanda do DfA é global; o leilão é por reino. Este comando junta as duas
coisas e responde “onde ponho este item?”:

```powershell
python -m woweconomy.analytics.realm_market --db tsm_markets.db
python -m woweconomy.analytics.realm_market --db tsm_markets.db --min-score 50
python -m woweconomy.analytics.realm_market --db tsm_markets.db --min-score 70 --csv realms.csv
python -m woweconomy.analytics.realm_market --kind mounts --db tsm_markets.db
```

Duas coisas que o cálculo tem de respeitar, e respeita:

- **Reinos ligados são um só mercado.** Stormreaver, Dragonmaw, Haomarush e
  Spinebreaker partilham o mesmo leilão e o TSM guarda o mesmo preço nos quatro
  nomes; o comando colapsa-os numa linha (`Dragonmaw +3`) para não os contar
  quatro vezes nem enviesar a mediana.
- **A referência é a mediana dos reinos, não o preço regional do TSM.** O
  `region_market` é uma média arrastada pelas mesmas listagens mortas que se
  querem desarmar: um pedido de 68k num item de 700g puxa a média e faz os
  reinos saudáveis parecerem 5x baratos. Por item, a referência é a mediana
  entre mercados, e `--realm-cap` (default 2x) corta um pedido antes de ele
  decidir o ranking.

O que ele NÃO diz: velocidade. `saleRate`/`soldPerDay` só existem por região
(um número para toda a EU), por isso a tabela mede o que se **pede** e quanta
concorrência há (`leiloes`), nunca “vende mais unidades aqui”. Colunas a ler
juntas: `vs mediana` (preço), `leiloes` (profundidade) e `cortes` (quantos
pedidos eram irreais -- perto da metade numa praça morta).

## De onde vêm os dados (TSM vs Blizzard API)

Regra: **preços e sinais = TSM**; **Blizzard API = só metadados de item**.

- **TSM `AppData.lua`** (escrito pelo TSM desktop app, tipicamente de hora a hora) —
  fonte principal: por reino `minBuyout`, `DBMarket` (média ponderada de 14 dias),
  `numAuctions`, `historical`; por região `DBRegionMarketAvg`, `DBRegionHistorical`,
  `DBRegionSaleAvg`, `DBRegionSaleRate` (fração dos posts que vende, a única medida
  de velocidade), `DBRegionSoldPerDay`. Zero chamadas de API.
- **CSVs públicos da TSM** (oficiais, sem chave nem conta) — rota alternativa sem
  app desktop, e a que alimenta `csv/`:
  `region/items.csv` (`marketValue,historical,avgSalePrice,saleRate,soldPerDay`),
  `realm/<realm>/items.csv` (`marketValue,minBuyout,recent,historical`) e
  `commodities.csv`.
- **Blizzard API** — a API de leilões devolve **apenas um retrato das listagens
  atuais** (~1h de cadência): não tem histórico, não tem preço médio, não tem
  `saleRate` nem vendas concluídas (impossível reconstruir `DBMarket` a partir daí).
  Um pedido de commodities consome **25 unidades de quota**, o limite é
  **36.000 chamadas/hora**, e os termos exigem apagar dados com mais de **30 dias**.
  Fica para o que só ela tem: `quality`/`binding`/`sellPrice` (`enrich_items.py`,
  `enrich_inventory.py`).

## Vendas reais: o diario (`scripts/journal.py`)

A heuristica tem suposicoes (`--target-posts`, `--undercount`, `--elasticity`); os
teus dados reais substituem-nas quando existirem.

**Journalator** (addon, ja instalado) guarda em `SavedVariables/Journalator_Statistics.lua`
por item e reino: `successes` (vendeu), `failures` (expirou), `totalSold`/`totalBought`
com contagem e valor. E dai que sai a tua verdade:

```powershell
python scripts/journal.py import     # Journalator -> journal_stats (copper)
python scripts/journal.py report     # tabela + calibracao + inflacao
```

O report mostra: vendas/expiracoes reais, **sell-through real**, **posts por venda
reais**, preco realizado vs a minha `posta` vs o `TSM venda`, e uma seccao
**"ja expiraram sem vender"** com a razao `posta/venda` (marca `inflacao` quando
>=3x). Se houver poucos dados (<3 itens ou <5 vendas) ele diz que sao poucos e
**mantem a heuristica** — nao inventa calibracao.

**Registar a mao** (vendas e reposts que o addon nao apanhar, ou para apontar o
que fizeste a seguir a um report):

```powershell
python scripts/journal.py log-sale --item "Wool Cloth" --price 5 --qty 99
python scripts/journal.py log-post --item 1351 --price 12632
python scripts/journal.py log-fail --item 1351 --note "expirou 48h"
python scripts/journal.py log-buy  --item 124640 --price 800 --qty 3
python scripts/journal.py import-csv journal.csv   # date;kind;item;price_gold;qty;note
python scripts/journal.py stats                    # o que esta guardado
```

O registo manual **conta para a calibracao** (sell-through, posts por venda, preco
realizado), somado ao do addon — nao e so uma nota. Tres regras que importam:

- **uma tentativa = um desfecho**: `log-sale` (vendeu) ou `log-fail` (expirou).
  Um **repost** e outra tentativa: se voltar a expirar, e outro `log-fail`. E
  assim que os reposts aparecem no racio em vez de o inflacionarem.
  `log-post`/`log-cancel` ficam de fora do racio (senao o anuncio contava 2x).
- o **reino e inferido** (o do addon; senao o mais frequente da base), para os
  teus registos fundirem com os do addon em vez de criarem uma linha paralela.
- se registares a mao algo que o addon **ja viu**, o report avisa que esta a
  contar 2x (o evento existe nas duas fontes).

Unidades: o pedido/cli fala em **gold**, a base guarda **copper** (convencao do
repo), como o resto dos sinais do TSM.

### Politicas de preco do `calc_price.py` (afinaveis)

O preco nunca vem de um so numero: cada distorcao conhecida tem regra propria.

| knobs | default | o que muda |
|---|---|---|
| `--undercount` | **2.20** | `saleRate`/`soldPerDay` só contam vendas de quem usa TSM, logo são um piso; calibrado em 204 vendas reais (1.0 = TSM puro) |
| `--sale-cap` | **3.0** | **sem parede local**, teto = `DBRegionSaleAvg x isto`; quando morde, o desconto por velocidade *não* se aplica por cima |
| `--realm-cap` | 2.0 | **com parede local**, teto = `max(mediana local, MinBuyout) x isto` |
| `--relist-cap` | 0.5 | o custo de relist esperado nunca passa isto do valor do item |
| `--target-posts` | **1** | no caminho "sem oferta", alvo de posts por venda |
| `--elasticity` | 1.0 | agressividade desse desconto (>1 corta mais) |

Regras sem knob: `DBRegionSaleAvg` (média de **compras**, com snipes/flips) **nunca** ancora o preço quando cai abaixo do `MinBuyout` atual — aí é prova de compra barata, não preço. E `LIQUIDAR` devolve o tier **Min** (preço de despacho), não o piso de vendor.

Os defaults acima vêm do diário real: ver a secção seguinte. A coluna `venda_x`
(quanto a minha `posta` é a venda média do TSM) mostra o desvio item a item.

## How the numbers work (resumo dos cálculos)

Money units: TSM and Blizzard money fields are **copper**; display divides
by 10,000 for gold. Missing prices are **excluded, never zero-filled**.

Per drop (probability `p`, mean qty `q`, reference price = `avgSalePrice`):

- `EV_GROSS = p x q x v`, `v = avgSalePrice x (1 - 5%)` (retail AH cut, assumption).
- No base+rate price multiplier exists in this repo: the reference price is
  used unscaled. (A `avg x (2 + 10 x sr)` formula would inflate every price
  2-12x without basis and is deliberately NOT applied.)
- `sale_rate` is TSM **DBRegionSaleRate**: fraction of listed region auctions
  that sell, verified 0-1 decimal scale. Per-LISTING sell-through with **no
  time dimension**. It is a liquidity indicator, never a daily probability.
- `EV_NET = EV_GROSS x sale_rate x VOL`, `VOL = 1` if `sold_per_day > 0`
  else `0.1` (thin-market haircut, documented assumption).
- Pricing multiplier (opt-in): effective list price
  `avg x (base + sr x rate_mult)`, floor `vendor x floor_mult`
  (`--price-base/--price-rate/--price-floor`, defaults 1.0/0.0/off =
  reference pricing, no silent change).
- `drop_rate` is the Wowhead `%` column (validated once, never clamped);
  `qty` = range midpoint (`1-4` -> 2.5, uniform assumption, samples unknown).
- `VENDOR_GOLD = p x q x Blizzard sell_price`: immediate gold, no AH.
- Days-to-sale is N/A: the metric cannot support it. No daily compounding.

Per NPC: `EV_GROSS_PER_KILL`, `EV_NET_EXPECTED_PER_KILL`,
`EV_EXPECTED_PER_HOUR` (@ `--kpm`), `VENDOR_GOLD_PER_KILL`,
`DATA_CONFIDENCE` = evidence share x freshness `1/(1+age_days/30)`
(coverage, NOT a sale probability; unknown age counts 0.5),
`JACKPOT_EV` (best weighted single hit + evidence: `spd`, `sr`, vendor),
`JACKPOT_PROBABILITY` (`P(>=1 drop in 100 kills)` - genuine drop probability),
`EXPECTED_DAYS_TO_SALE` = n/a.

Rankings: farms (EV_NET), vendor farms, recipes, BoE (Blizzard-verified
`ON_EQUIP` only - never name-guessed), mixed (>=2 pillars), mogs (by price),
mog EV / fast movers (`sr>=5%`) / thin (`sr<1%`) / vendor-fallback views,
mog farms (joint sell-through of what you plausibly loot in `--mog-kills`
kills, default 600; days n/a), jackpots (rare <10%, selling), mats
(units/kill), rotation (round-robin vs hyperspawn throttle).

**BEST GOLDBOUND SESSION** (`--session 15 30 60`, `--travel-sec`):
route vs best solo NPC with equal time assumptions (travel deducted from
route only; solo assumes no throttle - optimistic). Per plan: `vendor`
(received on the spot), `auction_est` (sale-weighted estimate, NOT
guaranteed), `speculative` (gross - net, may never sell), `conservative`
(vendor + fast movers `sr>=5%` only).

**Calibrating farm pace (P2)**: `--kpm`/`--travel-sec` are YOUR measurements,
not data. Measure in-game: kill one camp for 5 min and count (kpm), then
time one full rotation loop (travel). Start `--kpm 20 --travel-sec 60` and
replace after the first session. Compare solo vs route lines before committing.

Price freshness is printed every run (`as of ...` + STALE warning past 30d).
Prices come from `tsm_region_price` - the live regional table the DfA
estimate also reads - so the farm report and the in-game price quote one
source and one vintage. `--price-source legacy` reads the frozen
`market_snapshots` table and `--price-source csv` reads `csv/items.csv`,
both for A/B. Expected revenue is never guaranteed or immediately spendable.

## DFA Sentinel ML (validated predictions)

The game-facing estimates come from a versioned prediction layer on top of the
existing Journalator/TSM pipeline:

```powershell
python -m pip install -r requirements-ml.txt
python scripts/dfa_ml.py sentinel            # train, validate, promote
python scripts/dfa_pricing_export.py         # rebuild the addon dataset
```

It trains calibrated sale probabilities (24h/48h/168h), a realized-price model,
and two separate market-risk targets (undercut pressure and price decline),
against simple baselines on a chronological holdout. Time to sale is reported
but is not exported while its censoring-aware C-index stays below 0.60.

Every exported price carries an **80 % split-conformal interval** and the
coverage that interval actually delivered on a held-out block. The tooltip
prints both, for example:

```text
DFA estimate: 1.57g
  80% range: 0.83g - 2.99g (77% of 103 sales)
Expected realized: 1.57g
  80% range: 0.73g - 3.37g (85% of 119 sales)
```

A missing interval is `nil`, never a zero-width range; an old dataset simply
shows the point estimate.

Artifacts: `models/dfa_sentinel/<version>/` + atomic `CURRENT`.
Metrics: `reports/dfa_sentinel/sentinel_report.json`.
Full audit, measured numbers and limitations:
[reports/dfa_sentinel_ml.md](reports/dfa_sentinel_ml.md).
`watch.py` retrains only when enough new confirmed labels exist.

## Posting from Auctionator

The DfA estimate reaches the seller in Auctionator's selling tab, and two
things there are settings rather than decisions the addon makes for you.

**The price.**  Selecting an item fills the buyout field with the estimate.
The fill is not a lock: the moment you choose a price yourself -- by typing
it, or by clicking a row in Auctionator's price list -- the estimate stops
competing with you.  A row click is read from the `PriceSelected` event,
which carries the row and therefore its buyout, so the field ends up
holding the price you clicked rather than a number reconstructed
afterwards.  `Auctionator.GetChosenPrice()` and
`/dfaestimate fill` report which price that was.

That distinction matters because Auctionator writes a price for its own
reasons too -- its database, its market search, the vendor value of a piece
of equipment -- and those writes are indistinguishable from a click by
their value alone.  Only the event says which one happened.

**The hours.**  `/dfaestimate posthours 12|24|48` sets the auction
duration, which is what the deposit and the time the item has to sell both
follow.  It is stored in `DFA_ESTIMATE_DB` and written into Auctionator's
own `auction_duration` config, which is a dropdown *index* (1 = 12 h,
2 = 24 h, 3 = 48 h) rather than hours -- the mapping is read from
Auctionator's `AUCTION_DURATIONS` table, not guessed.

Only the three real durations are accepted; 18 hours is refused rather than
rounded, because rounding to 24 is a decision you did not make.  The
setting is pushed into Auctionator only after you have chosen one: adopting
a default we invented would be changing another addon's setting unasked.
If Auctionator is configured to save the last duration as the default, the
confirmation says so, because that turns this into a one-shot setting.

## The new-dataset alert

`run_pipeline.py` announces the dataset after the `export` task, over the
same channels the rest of the project uses (`DFA_DISCORD_WEBHOOK`, or a
desktop toast when no webhook is configured).  The state it compares
against lives in Postgres (`pipeline_stat`), and the digest is only
recorded once a channel actually took the message -- a webhook that was
down once must not lose the alert for good.

The comparison is on the dataset's *content*, not on the file.  That
distinction had to be measured: hashing the whole file covers
`generatedAt`, so every export looked new.  Two exports a minute apart were
diffed and differed in exactly two ways -- the timestamp, and `psell`
moving 0.1619 -> 0.1618 because the features include how long ago the
market was measured.  Nothing else in 1.37 MB changed.

So `dataset_content_signature()` strips the build time and compares floats
at two decimals (1%).  Prices are integers in the dataset and are
untouched; a probability or a factor that moves by more than 1% is still a
change.  The same function is what `run_pipeline.dataset_fingerprint()`
calls, so "did the dataset change" has one definition in the project.

Verified against the real pipeline: cycle 1 announced, cycles 2 and 3 --
same file -- returned nothing.
